## 2. LS11 컨테이너 (WORLDMAP.LZW)

정수는 전부 **빅엔디언**.

    0x000  "LS11" + 12바이트 0
    0x010  사전 256바이트  (심볼 번호 0~255 → 실제 바이트)
    0x110  항목 표: 항목당 12바이트 = (압축크기, 해제크기, 시작주소), 압축크기==0 이면 끝(끝 표지 4바이트)
    ...    항목별 비트 스트림 (시작주소부터 압축크기 바이트, 항목끼리 빈틈 없이 이어짐)

WORLDMAP.LZW 는 항목 3개 (= `worldmap.000/.001/.002`):

| 항목 | 압축크기 | 해제크기 | 시작주소 | 이름 |
|---|---:|---:|---:|---|
| 0 | 17,166 | 25,394 | 0x138 | worldmap.000 (유럽·아프리카·인도) |
| 1 | 14,586 | 21,973 | 0x4446 | worldmap.001 (동아시아·동남아) |
| 2 | 16,184 | 23,907 | 0x7D40 | worldmap.002 (신대륙) |

시작주소 0x138 = 0x110 + 12×3 + 4. 마지막 항목 끝 = 파일 끝 (48,248).

### 비트 스트림 (MSB 먼저)

수 하나 = `1` 이 k 개, `0` 하나, 이어서 (k+1) 비트 값 v → 수 = (2^(k+1) − 2) + v.

- 수 n < 256 : 리터럴, 출력 = 사전[n]
- 수 n ≥ 256 : LZ 복사. 거리 = n − 256 (≥ 1). 이어서 수 m 하나 더 읽고 길이 = m + 3. 출력 위치에서 거리만큼 앞에서 **바이트 단위**로 복사 (겹침 허용).
- 항목 끝은 0 비트로 채움. 해제크기에 도달하면 멈춘다 (실측: 원본 3개 모두 채움 비트 0~6).

「압축 크기 = 원래 크기면 무압축 저장」 같은 규칙은 **공개 소스에 없고** 우리 파일에서도 관측되지 않았다 (압축크기 < 해제크기 전부). 우리 압축기도 무압축 저장은 하지 않는다.

### 원본의 압축 방식 — 역공학으로 얻은 규칙 (바이트 동일 재현)

공개 도구의 압축기는 LZ 없이 리터럴만 쓰는 단순판이다(사전도 identity). 원본 `WORLDMAP.LZW` 는 그렇지 않으므로 원본 토큰열을 해제해 규칙을 추정·검증했다:

1. **사전** = 3개 항목 해제본 전체의 바이트 출현 빈도 내림차순 (3개 항목이 사전 공유). 동률 순서는 원본 도구의 정렬 구현에 따라 뒤섞여 있어 단순 규칙으로 재현되지 않는다(256개 중 126칸이 「동률 시 바이트값 오름차순」과 다름).
2. **LZ 파싱** = 느긋한(lazy) 최장 일치: 각 위치에서 길이 ≥ 3 인 최장 일치(동률이면 **가장 가까운** 거리)를 찾고, 바로 다음 위치의 일치가 더 길면 지금은 리터럴을 내보낸다. 최대 거리는 8190 이하 (관측 최대 8190·8187·8164, 한도 8192 로 두면 항목 2에서 토큰열이 어긋남. 8190/8191 은 이 데이터로 구별 불가 → 8190 채택).
3. 위 규칙으로 3개 항목 토큰열이 원본과 **토큰 단위로 전부 일치** (10,767 / 9,192 / 9,999 토큰).

**koukai2 패치본의 압축 방식**: LZ 복사 토큰이 **하나도 없는** 리터럴 전용이고 사전은 「전체 빈도 내림차순, 동률은 바이트값 오름차순」 — 카페 도구 출력은 `encode_pack(parts, window=0)` 과 **바이트 동일** (§6).

## 3. 대륙 파일(해제본) 구조

    0x0000~0x0A8B  2바이트 LE × 1350  = 「4분할 맵」 시작 오프셋 표 (가로 30 × 세로 45)
    0x0A8C~        4분할 맵 데이터 (표의 오프셋은 0x0A8C 를 0 으로 본 상대값)
    표 위치 = ((세로-1)×30 + (가로-1)) × 2      (세로·가로는 1 시작)

4분할 맵 하나 = 12×12 = 144 타일. 맵 데이터:

- 첫 바이트 b0 의 **최상위 비트가 1** → 맵 전체가 단일 타일(b0 & 0x7F)이고 **1바이트로 끝**. (0xFD·0xFC 가 대부분 = 균일한 바다로 보임)
- 최상위 비트 0 → b0 = **기본 타일**, 이어서 **18바이트 비트마스크**(144비트, 타일 0 = 첫 바이트의 MSB, 행 우선) + 마스크가 1 인 타일마다 코드 1바이트(타일 번호 순). 마스크 0 인 타일은 기본 타일.
  글의 「첫 1바이트(예 7b/7d)」가 이 기본 타일이다 (글의 첫 판 패치 `3e54: 7b->7d` 는 기본 타일 값을 바꾸는 방식. 우리 koukai2 패치본은 비트마스크 방식 — 기본 타일은 0x7b 그대로).

### 독립 검증 (글과 무관한 일관성 검사)

원본·패치본 각 3개 대륙 파일 × 1350 맵 전부에서:
- 오프셋 표 단조 증가 (동일값 인접 0건), 첫 항목 0.
- 「첫 바이트 최상위비트 1 → 길이 정확히 1」, 「0 → 길이 = 1 + 18 + 마스크 1의 개수」가 **예외 없이 성립** (예: worldmap.000 은 균일 890 + 마스크형 460 = 1350).

원본 코드 바이트 최댓값은 0xB7(worldmap.001)이라 **0xFF 는 원본에 없는 코드** — 패치가 운하 물 타일로 새로 쓰는 값.

### 인덱스 계산 재현 (글: 나일강 하류 = 표 위치 0x41A → 데이터 0x33C8 → +0xA8C = 0x3E54)

| 항목 | 값 |
|---|---|
| 표 위치 0x41A → 맵 번호 | 0x41A/2 = 525 = 17×30 + 15 → **세로 18, 가로 16** |
| 표의 값 | 0x33C8 |
| 절대 오프셋 | 0x33C8 + 0xA8C = **0x3E54** |
| 맵 끝 | **0x3EA3** (길이 80 = 1+18+61) |

글과 **전부 일치**.

## 7. 패치 로직 (`horiedit_py/data/canal.py`)

`Canal(key, name, edits, map_checks)` 상수 `SUEZ`, `PANAMA`, `CANALS`. 편집 = `(파일 번호, 해제본 오프셋, 전, 후)` — §4 표.

| 함수 | 동작 |
|---|---|
| `canal_state(parts, canal)` | `OPEN` / `CLOSED` / `UNKNOWN`. 모두 후 → OPEN, 모두 전 → CLOSED, 섞임·다른 값 → UNKNOWN. 오프셋이 기대 맵 번호(525 / 736·766)에 속하는지 표로 추가 확인(다른 판이면 UNKNOWN) |
| `canal_states(parts)` | 운하별 상태 dict |
| `set_canal(parts, canal, mode)` | OPEN(개통)·CLOSED(원상복원). UNKNOWN 이면 `CanalError` 거부. 입력 불변. 이미 목표면 복사만 |
| `read_worldmap(path)`, `file_canal_states(path)` | 파일 → (사전, 해제본), 상태 |
| `apply_canal_to_file(path, canal, mode, backup=True)` | 파일 수준 전환 |

- 수에즈·파나마 **서로 독립**. 복원은 **운하 바이트만** — 제주·울릉·독도는 `CAFE_EXTRA_EDITS` 로 기록만 하고 적용하지 않는다.

### 파일 쓰기·백업 전략
1. UNKNOWN 이면 거부 — 파일 그대로, 백업도 안 만든다.
2. 이미 목표 상태면 아무것도 쓰지 않는다.
3. **백업** `<경로>.canal-orig` 는 **없을 때만** 통째 복사(덮어쓰지 않음 → 최초 상태 보존). 복원 기능은 바이트 단위 복원이라 백업은 최후의 안전망.
4. 재압축은 **원본 파일의 사전과 압축 방식(LZ 여부)** 을 그대로 사용.
5. 재압축본을 다시 해제해 기대 해제본과 대조한 뒤 `.canal-tmp` 에 쓰고 `os.replace` 로 교체.

## 9. 한계

- **항구 자동 이동 항로**는 원본 항로표를 따르므로 운하를 쓰지 않는다 (글의 지적). 지도만 뚫은 것 — 직접 조종해 지나갈 수 있게 하는 패치. 항로표 위치는 아직 미분석(별도 과제).
- 코드 바이트(0xFF 포함)·기본 타일(0x78~0x7d)의 지형 의미는 미분석. 「0xFF = 항해 가능한 물」은 글과 렌더 모양에서의 추정이며 게임에서 확인하지 않았다.
- LS11 불확실성: ① 원본 사전 동률 순서(재현 불가 → 사전 재사용으로 해결), ② LZ 최대 거리 8190 vs 8191 (구별 불가).
- 제주·울릉·독도 변경(글 범위 밖)은 기록만, 기능으로 제공 안 함.

## 10. 시험 (`python -m unittest discover -s tests -v`)

29건. 합성 시험은 항상, `originalgame/` 실물 시험은 파일 없으면 skip.
- LS11: 왕복, 헤더 레이아웃, LZ 효과, 사전 인자 유지, 잘못된 입력 거부, 원본 바이트 동일, 카페본 바이트 동일(리터럴 전용).
- 운하(합성): 상태 3종, 개통→복원 왕복, 독립, 운하 바이트만 변경, 복원이 제주 등 안 건드림, 부분 변경·다른 값·다른 판 → UNKNOWN+거부, 입력 불변.
- 운하(파일): 백업 최초 1회·미덮어쓰기, UNKNOWN 이면 파일·백업 무변경, 이미 목표면 무변경.
- 운하(실물): 전 값 12개, 카페본 두 운하 OPEN, 변경 19바이트=글 목록, 파이썬 패치=카페본, 원본→개통→복원 동일, 카페본에서 수에즈만 복원 시 제주 등 유지, 전 맵 구조 검사.

## 11. 2단계(GUI·게임 실측) 체크리스트

1. 원본 WORLDMAP.LZW 를 우리 도구로 수에즈 개통해 DOSBox 실행 — 게임이 우리 압축본(원본과 같은 사전·LZ 규칙)을 읽는가.
2. 개통 후 수에즈(세로 18, 가로 16 맵 열 9 행 5~10)를 직접 조종으로 통과 가능한가. 지중해·홍해 접속 지점에서 좌초·진입 불가가 없는가.
3. 파나마(북 맵 736 + 남 맵 766 3칸) 개통 후 대서양↔태평양 통과 가능한가. 3칸이 연속 통과되는가.
4. 원상복원 후 원본처럼 막히는가. 수에즈만/파나마만 따로 전환 시 다른 쪽이 영향받지 않는가.
5. 카페 패치본에서 수에즈만 복원해도 제주·울릉·독도가 그대로인가(게임에서 확인).
6. 「알 수 없음」 상태(한 바이트만 다른 파일)에서 GUI 가 전환을 막고 사유를 보여 주는가.
7. 항구 자동 이동 항로는 운하를 쓰지 않음을 확인하고 README/도움말에 한계로 적는다.
8. 개통 상태에서 세이브 로드·저장·장시간 항해 후 이상(좌표 이탈, 충돌 판정) 유무.
9. 백업 `WORLDMAP.LZW.canal-orig` 가 첫 전환 때만 생기고 두 번째 전환에서 안 덮이는지.
10. 게임이 LZ 압축본·리터럴 전용 압축본을 모두 읽는지 (카페본이 읽히면 리터럴 전용은 안전).
11. 대상 파일 위치·대소문자: 레포 안 koukai2 는 `worldmap.lzw`(소문자), 원본은 `WORLDMAP.LZW`. GUI 가 찾을 파일명 규칙 결정.
