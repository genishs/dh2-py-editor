# MAIN.EXE 분석 — 함선 신조 데이터 테이블

> 분석 대상: `D:\Documents\workspace\study\koukai2_edit\originalgame\koukai2\MAIN.EXE` (288823 byte, DOS MZ 16-bit 실행파일)
> 도구: Python 3.14 (`py` launcher), 휴리스틱 슬라이딩 윈도우 검색 + KOUKAI2.DAT 슬롯 데이터와의 cross-match.

## 1. 파일 구조

- MZ 헤더 e_cparhdr=0x540 → 헤더 끝 = `0x5400`
- 코드/데이터 영역: `0x5400 ~ 0x46837`

---

## 2. [확정] 함선 ROM image 위치

KOUKAI2.DAT 의 10개 슬롯 모두에서 ship4_addr=`0x5291` 및 s_addr=`0x501D` 영역의 첫 24 byte 가 EXE 내 단일 위치에서 매칭됨 → 100% 확정.

| 데이터 | EXE 오프셋 | 크기 | 의미 |
|---|---|---|---|
| **Ship5 ROM** (이름/sform/bform) | `0x405FD` | 25 × 25 = 625 byte | 함선 25종 이름·외형 원본 |
| **Ship4 ROM** (lrudder/lsail/lcrew/dcrew/capacity/lnowea/none[5]) | `0x40871` | 25 × 12 = 300 byte | 함선 25종 정적 스펙 원본 |

**의의**: horiedit 의 `org_ship_edit` 가 KOUKAI2.DAT 슬롯 내 사본을 편집하는 반면, 여기 MAIN.EXE 의 ROM 을 편집하면 **새 게임 시작 시점**의 모든 슬롯에 적용된다.

## 3. [유력 추정 — 검증 필요] 신조 데이터 군집

`0x42100 ~ 0x42800` 영역에 25-원소 uint16 LE (50 byte) 테이블이 다수 packed 되어 있음을 슬라이딩 윈도우 검색으로 확인.

### 3-1. 테이블 A: 신조에 필요한 항구 공업 수치 — **1순위 후보 `0x42722`**

uint16 LE × 25 (50 byte):
```
[2, 2, 3, 2, 2, 12, 6, 5, 5, 70, 12, 5, 4, 10, 45, 6, 40, 16, 18, 20, 38, 42, 42, 40, 32]
인덱스: BALS HANJ DAWO BUS  TARE RATI REDO BRIG NAO  KARA GAL  JEBE PANE SLOO PREG BAG  SHIP JUNK LGAL PGAL BGAL RA   CHEO AN   GWAN
```
- 1~99 범위 부합, size 상관계수 0.632
- **변칙**: KARA(9)=70 — 다른 중형보다 너무 큼. 이 위치가 dcrew 일 가능성도 있음

헥스 덤프:
```
03 00 02 00 02 00 03 00 02 00 02 00 0C 00 06 00 05 00 05 00 46 00 0C 00 05 00 04 00 0A 00 2D 00 06 00 28 00 10 00 12 00 14 00 26 00 2A 00 2A 00 28 00 20 00
```

### 3-2. 테이블 B: 신조 시 최대 내구도 (lhull) — **1순위 후보 `0x424AE`**

uint16 LE × 25 (50 byte):
```
[25, 30, 20, 80, 45, 8, 35, 30, 35, 15, 40, 50, 15, 20, 85, 90, 20, 70, 65, 70, 280, 120, 105, 40, 250]
```
- BALS=25 (작음), GWAN=250 (큼). corr 0.587
- **변칙**: LGAL(18)=280 이 1byte 범위 초과 → Ship1.lhull (unsigned char) 과 모순. `& 0xFF` 시 24 로 wrap.

헥스 덤프:
```
37 00 2D 00 1E 00 28 00 05 00 1E 00 46 00 19 00 1E 00 14 00 50 00 2D 00 08 00 23 00 1E 00 23 00 0F 00 28 00 32 00 0F 00 14 00 55 00 5A 00 14 00 46 00 41 00 46 00 18 01 78 00 69 00 28 00 FA 00
```

### 3-3. 대안 후보 (모두 0x42100~0x42800)
- `0x4252E` — `[30,20,15,85,50,10,15,25,30,50,37,52,12,25,82,88,18,68,67,100,270,110,95,30,270]`
- `0x425AE` — `[16,12,10,65,45,7,55,15,35,6,28,55,8,10,80,80,20,80,70,60,120,40,75,50,150]`
- `0x42790~0x427F0` 부근 추가 후보들

## 4. Python 구현가 가이드

### 4-1. Ship4/Ship5 ROM 편집 (확정)
```python
SHIP5_ROM_OFFSET = 0x405FD
SHIP4_ROM_OFFSET = 0x40871

# Ship5 ROM 한 항목 = common.Ship5 (25 byte) 와 동일 포맷
# Ship4 ROM 한 항목 = common.Ship4 (12 byte) 와 동일 포맷
# 25개 항목, 인덱스 0..24 = BALS..GWAN
```

### 4-2. 추정 테이블 (사용자 검증 필요)
```python
KOGYO_TABLE_OFFSET = 0x42722   # 추정: 신조 항구 공업 수치
LHULL_TABLE_OFFSET = 0x424AE   # 추정: 신조 시 lhull
# 둘 다 uint16 LE × 25 (50 byte)
```

### 4-3. 안전 가드
- 편집 전 MAIN.EXE.bak 백업이 있음. 필요 시 사용자에게 안내.
- 추정 테이블 편집 메뉴는 **반드시 "추정 — 사용자 검증 필요"** 경고를 표시.
- 값이 변칙(280 같은 0xFF 초과)이면 그 자리는 다른 데이터일 수 있음 → 변경 시 게임 동작 이상 가능.

## 5. 미확인 / 위험

1. 두 추정 테이블의 정확한 단일 25-원소 위치 미확정. KARA=70 (테이블 A), LGAL=280 (테이블 B) 변칙이 의심점.
2. 두 테이블이 단일 연속 25-원소가 아니라 **함수 내부 case/switch 인라인** 일 가능성 — 이 경우 슬라이딩 검색 불가.
3. 0x40871 Ship4 ROM 의 [13]번 SLOO부터 12 byte 패킹과 어긋난다는 분석가 노트 — 다만 horiedit.h 의 정의와 KOUKAI2.DAT 의 실제 데이터 모두 12 byte 패킹과 일치하므로 단순 노이즈 가능성.

## 6. 권장 검증 단계 (사용자/추가 분석가 작업)

1. DOSBox + IDA Free 로 0x40871 (확정 Ship4 image) cross-reference 코드 분석. 신조 코드의 CMP/MOV 즉시값 추적.
2. 게임 메모리 덤프로 lhull 테이블 직접 식별.
3. 추정 테이블 위치에서 한 함선만 변경 후 게임 실행 → 동작 확인.
