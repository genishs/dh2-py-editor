# analysis_O — MAIN.EXE 항해사 카탈로그 (인물 원본 테이블)

**상태**: 위치·구조 확정. 월급료는 **여기 없음이 확인됨**(미해결 과제로 남음).
**출처**: 2026-06~07 탐색 산출물 (`catalog_full.txt`, `navigator_list.txt`, `compare.txt`, `hired_navigators.txt`, `hired_exe_match.txt`, `salary_search*.txt`). 이 문서가 그 raw 덤프의 요약이며, 원본 파일은 같은 폴더에 보존한다.

---

## 1. 위치와 크기 (확정)

```
CAT_START = 0x03BBF2
레코드 크기 = 50 byte  (= Person.SIZE, 세이브의 인물 구조체와 동일)
레코드 수   = 120
카탈로그 영역 = [0x03BBF2, 0x03D362)      # 0x1770 = 6000 = 120 × 50
```

`0x03D362` 부터는 카탈로그가 아니다. 그 자리의 레코드(#120 `집사 마르코`, #121 `모데나공 호안`)는 이름 필드가 **비이름 바이트**이고 `exp_battle=8713`, `exp_sail=42421` 같은 비현실적 값이 나온다 → **경계는 120에서 끊는 것이 맞다.**

## 2. 레코드 구조 = `Person` 그대로

MAIN.EXE 카탈로그 레코드는 세이브의 인물 레코드와 **같은 50 byte 구조**다
([`horiedit_py/common.py`](../horiedit_py/common.py) 의 `Person`, `_FMT = "<13s13s2s8B2B2H4B2sBB"`).

| 오프셋 | 필드 | 비고 |
|---|---|---|
| +0 | `fname[13]` | 성 (CP949) |
| +13 | `lname[13]` | 이름 (CP949) |
| +26 | `none[2]` | 용도 미상 |
| +28 | `command` `sail` `know` `hunch` `tool` `sword` `charm` `death` | 능력치 8종 |
| +36 | `l_sail` `l_battle` | 레벨 2종 |
| +38 | `exp_sail` `exp_battle` | 경험치 2종 (u16) |
| +42 | `age` `none1` `pos` `port` | `none1` = 충성도 |
| +46 | `none2[2]` | 용도 미상 |
| +48 | `ability` | 비트필드 (td\|ac<<1\|gu<<2\|mp<<3\|me<<4) |
| +49 | `none3` | 용도 미상 |

## 3. 배열 순서

앞 6개는 **주인공**이고, 그 뒤가 항해사다.

| # | catalogID(`pos`) | 인물 | EXE 주소 |
|---|---|---|---|
| 0 | 0 | 페레로 조안 | `0x03BBF2` |
| 1 | 10 | 에란초 카탈리나 | `0x03BC24` |
| 2 | 30 | 스피노라 옷토 | `0x03BC56` |
| 3 | 50 | 로페스 에르네스트 | `0x03BC88` |
| 4 | 40 | 콘티 피에트로 | `0x03BCBA` |
| 5 | 20 | 베자스 알 | `0x03BCEC` |
| 6.. | 1,2,3,… | 일반 항해사 | `0x03BD1E` … |

주인공의 catalogID 는 **0/10/20/30/40/50** 이며 `horiedit_py/data/person.py` 의 `HERO_CATALOG_ID` 와 일치한다. 배열 순서(#3=에르네스트)와 ID 순서(50)가 **다르다** — 인덱스로 ID 를 추정하지 말 것.

배열 끝쪽에는 `pos=254`, `pos=255` 인 레코드가 섞여 있다(예: `알렘켈 로코`, `로우 로버트`). `pos=254` 는 **아직 아무에게도 소속되지 않은 상태**로 보인다 — 4절 참조.

## 4. 카탈로그(원본) vs 세이브(현재) — 무엇이 변하는가

동료로 고용된 인물을 양쪽에서 대조한 결과(`compare.txt`, 13명), **대부분의 필드가 그대로 복사**되고 다음만 달라진다.

```
=== 사누드 프랑코 (catalog #72) ===
        field |  CATALOG |     SAVE
      command |       71 |       71      ← 능력치는 전부 동일
         sail |       55 |       55
     exp_sail |      140 |     1224   <diff>   ← 플레이로 누적
          pos |      254 |       10   <diff>   ← 254(무소속) → 10(카탈리나 동료)
        none3 |       97 |      225   <diff>
   none2(+46) |     00f1 |     06f1   <diff>
```

즉 **`pos` 가 소속을 결정**한다: 카탈로그의 `254` 가 세이브에서 주인공 catalogID 로 바뀌면 그 주인공의 동료가 된다. 이는 [`analysis_K_companion_mechanism.md`](analysis_K_companion_mechanism.md) 의 동료 등록 메커니즘과 같은 이야기다.

`none1`(충성도)은 세이브에서만 의미가 있고 카탈로그 값은 초기값이다 (`hired_navigators.txt` 실측: 동일 세이브 안에서 10~100 으로 제각각).

## 5. 🔴 월급료는 이 50 byte 안에 없다

동료 항해사의 **월 급료**(개빈 10 / 필리 20 / 라울 20 / 야곱 20 을 anchor 로 사용)를 찾으려 했으나:

- 세이브 인물 레코드 50 byte 전 오프셋 대조 → **일관 일치 없음** (선행 조사)
- 카탈로그 레코드 50 byte 대조 → `salary_search.txt`: **0 후보**
- `none` 바이트 인덱싱 가설 → `salary_search2.txt`: **0 후보**

**결론**: 급료는 인물 레코드가 아니라 **별도 테이블**에 있거나, 능력치에서 파생 계산된다. 후자라면 [`analysis_H_ship_price.md`](analysis_H_ship_price.md) (항구 평균가) 처럼 "직접 편집 불가" 결론이 날 수 있다. 다음 시도는 **급료 anchor 값(10/20)을 카탈로그 인덱스로 정렬한 별도 배열**을 EXE 전역에서 찾는 방향.

## 6. ⚠️ 이름 바이트 검색의 오탐

`hired_exe_match.txt` 는 세이브의 이름 바이트를 EXE 에서 역검색한 결과인데, **짧은 이름은 대량 오탐**이 난다.

```
핏치 라울   : fname=b6 f3 bf ef  EXE=['0x3cf48']                    ← 유일, 신뢰
코사 판     : fname=c6 c7        EXE=[10곳: 0x123fb, 0x35d91, ...]  ← 2 byte라 무의미
```

**규칙**: 이름 검색으로 레코드를 특정할 때는 (a) 결과가 카탈로그 영역 `[0x03BBF2, 0x03D362)` 안에 있는지, (b) 후보가 1개인지를 반드시 확인한다. 4 byte 이하 이름은 이 방법으로 특정하지 말 것.

## 7. 남은 것

- `none`(+26) · `none2`(+46) · `none3`(+49) 의 의미 미상. `compare.txt` 상 `none3`·`none2` 는 고용 시 바뀌므로 **상태 플래그일 가능성**이 있다.
- 월급료 테이블 (5절).
- 카탈로그 편집 기능은 아직 GUI 에 노출하지 않았다 — 원본을 고치면 **신규 등장 인물 전체**에 영향이 가므로 영향 범위 확인이 먼저다.
